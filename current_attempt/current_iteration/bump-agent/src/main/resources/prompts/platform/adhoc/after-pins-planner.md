NOTHING MANAGES THIS MODULE, SO A DIRECT PIN IS THE RIGHT ANSWER AND NOT AN OVERRIDE. On a managed
module the version that clears a CVE belongs in the manager, and writing it onto the artifact takes
that artifact out of the set for good. Here there is no set and no manager, so the number goes on
this module's own declaration, and a plan that says so is a correct plan rather than a workaround.

NEARLY EVERY FLOOR IS RAISED IN THIS PHASE, so nearly every version question this project has is
this plan's question. The list is long because only what javac itself cannot start without was done
before the bump; what is here is what the test run and the scanner will need, and it is landing on a
module that has already compiled and will not be compiled again until the repository gate.

THE ROWS ABOVE NAME THE MANAGED SPELLINGS OF A LINE, AND THIS MODULE IS EITHER ON THAT LINE OR IT IS
NOT. No Boot parent reaches it and it imports no Boot BOM, or the stage above would not have
answered adhoc, so neither coordinate can appear in declared_versions and their absence settles
nothing. A module that declares spring-boot-starter-web, spring-boot-starter-data-jpa or
spring-boot-starter-test one at a time, each carrying a version of its own, is on the line that row
names and below its floor. Name the artifacts this module actually declares, the one version they
are to land on, and where each version lives: a set held in a single property is one edit, and the
same set written out as three literals is three. Where the module declares nothing on that line,
NOTHING-OUTSTANDING is the whole answer, and here it is the common one.

A SET IS ONE ITEM IN THE PLAN AND EVERY MEMBER IS NAMED IN IT. Artifacts move as sets even where
nothing declares the set, and the rows above give the members separately or not at all:
tomcat-embed-core with tomcat-embed-el and tomcat-embed-websocket, which share a version by contract
though only core is a row; byte-buddy with byte-buddy-agent; archunit with archunit-junit5; jaxb-api
with jaxb-runtime; every org.springframework.boot artifact in a module on one number. Three things
in declared_versions give a set away, and all three are readable without running anything: several
coordinates in one group carrying the identical version, several dependencies reading one property,
and a pair of names that are two halves of one release. A plan that names one member has planned a
split set, and a split set fails where one member calls another rather than where either was
declared, which is a place no compile visits.

A FLOOR ARTIFACT THIS MODULE NEVER DECLARES CAN STILL BE ON ITS CLASSPATH, arriving under something
it does declare: mockito-core carries byte-buddy. declared_versions reports what the files say, so
it cannot show you that. Where a declared artifact carries it, plan the carrier and say that is what
you are doing. Where nothing does, say where the pin has to go instead, dependencyManagement on
Maven or a constraint on Gradle, because that placement cannot be read off a coordinate.

WHAT A RAISE DRAGS UNDERNEATH IT IS THIS LANE'S OWN PROBLEM, because nothing here reconciles a
graph. An artifact raised to clear a floor brings newer transitives under something else this module
declares that was built against the older ones, and the framework crossing is that at its largest:
Spring's 3 line is jakarta where its 2 line was javax, and the Tomcat this module declares for
itself does not follow unless the plan moves it. Say which other declarations here read the artifact
you are raising. The stage below holds no build, so what the plan leaves unsaid is found at the
repository gate or not at all.
