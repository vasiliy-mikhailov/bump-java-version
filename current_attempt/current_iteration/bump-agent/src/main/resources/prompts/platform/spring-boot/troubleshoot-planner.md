THE REGIME: SPRING BOOT MANAGES THIS MODULE'S VERSIONS, and where this gate sits in the walk decides
what that means. This hop has raised the member floors and moved the target; the Boot line itself is
raised by the stage that runs after this gate. So Boot here is either where the project has always
kept it or where a previous hop's after-pins left it, and reading the parent version out of the
build file is the first thing that separates the campaigns below.

A SIXTH FAMILY, ALONGSIDE THE FIVE ABOVE: the managed set and the module disagree. It has three
shapes here and they call for different campaigns.

An override that did not take. The floors this hop raised before the JDK moved are members of the
set, so on a Boot module they are raised by overriding a version rather than by declaring one, and
an override written where the set does not read it changes nothing while reporting success. The
campaign then opens on the floor's own failure after a stage said the floor was met: a Lombok
ExceptionInInitializerError that never names Lombok, or a Mockito that cannot mock a class. Finished
means the artifact resolving at the floor, which inspect_jar can show, not an edit to the source
that consumed it.

A Boot line that moved on an earlier hop. Then the source is still written for the old one: javax
where the new line wants jakarta, a configuration extending a class that no longer exists, a
META-INF/spring.factories in this module's own resources that the new line does not read. Count
before naming this campaign. A grep for javax across the module is the difference between three
edits and three hundred, and three hundred is a different answer with a different ending.

A train left behind. The Boot migration recipe chains the Spring Cloud line and the property renames
along with the parent, so a module whose Boot moved while its spring-cloud-dependencies stayed is
the fingerprint of a version that was typed instead of migrated. That train is the campaign, and no
amount of source editing substitutes for it.
