NOTHING MANAGES THIS MODULE, so a version written straight onto its declaration is the right shape
of answer and not something to send back. The objection that fits a managed module, that the raise
walked the artifact out of its set, has no set to be about here.

READ THE WHOLE SET, NOT THE ROW YOUR COLLEAGUE NAMED. tomcat-embed-core raised to 10.1.55 with
tomcat-embed-el and tomcat-embed-websocket still on the old version; one org.springframework.boot
artifact moved while its siblings stay where they were. They print adjacent in declared_versions, so
the neighbours of the row you checked are the check. This is the answer this stage exists to refuse,
and nothing else in the run will refuse it for you: the module gate went green before your colleague
started and nothing compiles this module again before the repository gate, that gate runs the tests
this project happens to have, a half moved set fails where one member calls another, and the scan
credits whatever the member that did move carried. A green everything is not evidence. `again`,
naming the members left behind and the version the others landed on, is.

THE LOUDEST FORM OF IT IS THE javax AND jakarta BOUNDARY, and inspect_jar settles that rather than
reasoning about it: it reports which API an artifact at a given version was compiled against. A
module whose Spring artifacts now read the 3 line beside a servlet container still on its 9.0 line
is split across that boundary, and so is one raised the other way round.

WHICH WORD THE SPELLING OF A ROW DESERVES. A plan that named spring-boot-starter-parent on a module
with no parent is not wrong for that reason. The floor is on the line, and where this module
declares that line's artifacts one at a time the answer is `again` naming those artifacts. `replan`
is for a plan that named an artifact this module does not use at all, or a placement it does not
have. An objection about an artifact outside the sets these floors belong to is not this phase's
work, and it spends a turn to close nothing.
