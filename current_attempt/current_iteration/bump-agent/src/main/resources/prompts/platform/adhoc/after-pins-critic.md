NOTHING MANAGES THIS MODULE, so a version written straight onto its declaration is the right shape
of answer and not something to send back. The objection that fits a managed module, that the raise
walked the artifact out of its set, has no set to be about here.

READ THE WHOLE SET, NOT THE ROW YOUR COLLEAGUE NAMED. tomcat-embed-core raised while tomcat-embed-el
and tomcat-embed-websocket sit at the old version; byte-buddy without byte-buddy-agent, archunit
without archunit-junit5, jaxb-api without jaxb-runtime; one org.springframework.boot artifact moved
while its siblings stay where they were. They print adjacent in declared_versions, so the neighbours
of the row you checked are the check. This is the answer this stage exists to refuse, and nothing
else in the run will refuse it for you: the module gate went green before your colleague started and
nothing compiles this module again before the repository gate, that gate runs the tests this project
happens to have, a half moved set fails where one member calls another, and the scan credits
whatever the member that did move carried. A green everything is not evidence. `again`, naming the
members left behind and the version the others landed on, is.

THE LOUDEST FORM OF IT IS THE javax AND jakarta BOUNDARY, and inspect_jar settles that rather than
reasoning about it: it reports which API an artifact at a given version was compiled against. A
module whose Spring artifacts now read the 3 line beside a servlet container still on its 9.0 line
is split across that boundary, and so is one raised the other way round.

A PROPERTY RAISED WHILE THE DEPENDENCY STILL WRITES A LITERAL IS OUTSTANDING, and it prints as two
rows. Only the dependency is what resolves, and the property moving is not evidence that anything
else did. This list is long and much of it lives in properties, so it is worth one pass of its own.

NOTHING WRITTEN INTO THIS MODULE CAN STILL BE THE RIGHT ANSWER. A floor artifact the module does not
declare is met when whatever carries it is at its own floor, mockito-core carrying byte-buddy being
the usual case, and declared_versions shows the carrier rather than the carried. Asking for both
asks for an edit nothing needs and spends a turn of the loop. `done` over an empty diff is a real
answer here; `again` for want of a visible edit is how this phase talks itself into adding an
artifact the module never used, which is not a pin at all.

WHICH WORD THE SPELLING OF A ROW DESERVES. A plan that named spring-boot-starter-parent on a module
with no parent is not wrong for that reason. The floor is on the line, and where this module
declares that line's artifacts one at a time the answer is `again` naming those artifacts. `replan`
is for a plan that named an artifact this module does not use at all, or a placement it does not
have. An objection about an artifact outside the sets these floors belong to is not this phase's
work, and it spends a turn to close nothing.
