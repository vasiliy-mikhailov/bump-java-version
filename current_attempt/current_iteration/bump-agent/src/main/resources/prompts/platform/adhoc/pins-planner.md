NOTHING MANAGES THIS MODULE'S VERSIONS. Every row declared_versions prints for it carries a
number the module itself wrote, so there is no manager to move instead of the artifact, and
each floor it sits below is its own item in the plan.

A row that names a manager is the exception, and it is worth settling before planning
anything else: declared_versions prints the manager's coordinates beside a blank version, and
on a module answered adhoc there should be none. Where one appears, that artifact is managed
after all, and a version written here overrides a set nothing else will reconcile. Name the
artifact and its manager rather than the number.

A FAMILY IS ONE ITEM, NOT SEVERAL ROWS. The floors above list members separately: byte-buddy
with byte-buddy-agent, archunit with archunit-junit5, jaxb-api with jaxb-runtime,
tomcat-embed-core with tomcat-embed-el and tomcat-embed-websocket, which share a version by
contract. A managed set moves a family together and nothing here does, so a plan that names
one member has planned a split pair, and a split pair fails where one half calls the other
rather than where either was declared.

A floor artifact this module never declares can still be on its classpath, arriving under
something it does declare: mockito-core carries byte-buddy. declared_versions reports what
the files say, so it cannot show you that. Where a declared artifact carries it, plan the
carrier and say that is what you are doing. Where nothing does, say where the pin has to go
instead, dependencyManagement on Maven or a constraint on Gradle, because that placement
cannot be read off a coordinate.

A module that declares Spring artifacts one at a time is still on Spring's lines even though
nothing manages it, and the rows above that name Boot apply to it as written.
